## Що спрацювало

- Межі, contracts і порядок A → B зафіксовано у foundation до fan-out. CI та multi-agent сервіс не ділили свої внутрішні файли.
- Кожен агент мав native worktree та ізольовані integration databases; спільний живий сервер запущено після композиції.
- Merge conflict був один: Drizzle journal. Обидві міграції та snapshot chain збережено; mandatory PostgreSQL suite пройшов без skips.
- Незалежний reviewer повертав зауваження до інтеграції; фінальна перевірка охопила продукт, автономний runner і contracts.

## Де знадобилась переробка

- Hosted A виявив спільний test fixture із вісьмома enabled agents після введення ліміту 1–5. Fixture ізольовано; cap і негативні кейси залишились чинними. Один correction turn A.
- B після оновлення від A мав повторну перевірку міграцій, автономного bundle та installation bootstrap. Це залежна інтеграція, включена до його turn intervals.
- Браузер виявив пропущений `ci` у whitelist вкладок. Додано один тест фактичного page route.
- Реальний Actions event виявив неправильне використання `repo.fork`; виправлено порівняння origin IDs. Наступний старий demo event усе ще посилався на попередній base SHA; demo оновлено від виправленої бази.
- Після справжнього SQL CRITICAL артефакта Windows CRLF/GitHub LF відмінність зупинила strict import. Виправлено тільки еквівалентність newline bytes; зміни команд та інші provenance mismatch залишаються відхиленими.
- Один Studio timeout і один успішний retry збережено в історії. В окремому failure scenario відсутність OpenRouter key не знищила два успішні результати.

Root виконав 5 followup_task calls. Це повторні review/repair dispatches, а не достовірна кількість уточнень людини. Внутрішні читання окремих великих файлів не агрегувались, тому точний обсяг дубльованого контексту — n/a.

## Рекомендації для наступного запуску

1. Brief агента A: явно визначити fixture factory і кількість enabled agents у shared DB; це зменшить переробку через міжтестове забруднення.
2. Brief агента B: включити internal PR у fork-репозиторії та LF/CRLF round trip у acceptance matrix до експорту; це перенесе знайдені runtime помилки у дешеві регресійні тести.
3. Orchestrator: перевіряти actual route query для кожної нової вкладки після production build; це раніше виявить розрив між компонентом та page whitelist.
4. Security CI profile: окремо вимагати коректний finding kind та узгоджені evidence components. Qwen правильно знайшов SQL injection, але помилився у додатковій класифікації; positional grounding цього не перевіряє.
